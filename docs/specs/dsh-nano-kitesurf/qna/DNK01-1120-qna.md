## 3. 逐题裁决

### Q1 — agent 的「打开页面」面放在哪里？

**已确认的断点**：skill 加载失败（`resourceBase`）→ 拿不到「走 relay」的知识；`POST /open` 需 GUI cookie（401）；桥**没有**导航类 MCP 工具。三者叠加后，agent 只剩裸 CDP，而裸 CDP 连 `:8798` 会造私有页。

| 选项 | 内容 | 评价 |
|---|---|---|
| **A（推荐）** | 新增宿主 MCP 工具 `sandbox.open {url}`，内部复用 `POST /open` 的同一 handler；鉴权沿用宿主 MCP 既有准入，**不新开凭证面**；`/open` 的 REST 鉴权保持不变 | 一条与人等价的打开面；agent 无需 cookie；不扩大信任边界 |
| B | 放松 `/open`：让无 cookie 的本机请求通过 | **反对**。等于拆掉 `requestRejection` 这条鉴权边界（`route-guard:204`），所有路由一起失守 |
| C | 不加工具，只修 skill 让人/agent 都靠 relay + 裸 `Page.navigate` | 可行但没解决「打开」这个动作的语义；错误处理、`argSummary`、`incidentId` 全部拿不到 |

**推荐 A**。理由：Q1 的本质不是"缺一条 CDP 连接"，而是**缺一个语义化动作**。relay 只能发原始 CDP，没有 `/open` 的错误分类（`navigate.*`）、审计行与 hint。给桥一个薄工具，让它与人共享同一条实现，比让每个 agent 自己拼 CDP 更符合「单一真源」。

**批准后落地**：`mcp-bridge.mjs` 增 `sandbox.open`（`tools/list` + dispatch）、转发到 `/open` 同一 handler；`skills/kitesurf-cdp/references/routes.md` 与 SKILL 索引登记；测试：MCP `tools/call` → 与 REST `/open` 同结果同 errorId。

### Q2 — relay 接入如何让人看见？

**已确认的断点**：`makeCdpRelay`（`:199`）零处引用 `control`；`control.lastAction/lastCallAt` 只由 MCP tools/call 写（`:893`）；pane 控制条只读 `humanHold||writer`（`client:2784`）。→ agent 用 relay 驱动页面时，**界面上没有任何归属信息**。

| 选项 | 内容 | 评价 |
|---|---|---|
| **A（推荐）** | `/control` 增只读字段 `relay:{conns,lastAt,lastMethod}`（relay 接入/断开/最近一次写方法时更新）；pane 控制条条件扩为「`humanHold` ∨ `writer` ∨ `relay.conns>0`」，文案区分「MCP 写入中」与「agent 经 relay 接入」 | 最小可观测面；不改写权语义；人一眼看出谁在动 |
| B | 只在 `/health` 加计数，不动 pane | 计数已在（`conns/accepted`），但人要主动开诊断页才看得到，等于没解决 |
| C | 不改 | Q2 未闭合 |

**推荐 A**。理由：可观测性必须出现在**事件发生的那块界面**上（[dsh工作台] 的 pane），而不是另一个诊断页。字段是纯增量只读，不构成新的写入承诺。

**批准后落地**：`mcp-bridge.mjs` 的 relay 连接/断开/写方法处更新 `control.relay`；`controlSnapshot()` 透出；`client` 控制条渲染与 i18n 文案；测试：relay 连上后 `/control` 出现 `relay.conns>0`。

**需你确认的一点**：`relay` 是新公共字段 —— 这属**扩约**，请明确批准"新增只读字段"这件事本身。

### Q3 — 人的接管要不要真能拦住 relay？

**已确认的断点**：`humanHold` 的拒绝在 `:706`，**只覆盖 MCP tools/call**。relay 的 `Page.navigate` 完全绕过。→ 后果不是"agent 不能操作"，而是**人不能拒绝 agent 操作**，UI 上的「停止写入」是空承诺。

| 选项 | 内容 | 评价 |
|---|---|---|
| **A（推荐）** | `humanHold.active` 时，relay 对写类命令（`Page.navigate`、`Input.dispatch*`、`Runtime.evaluate`）**先记 `lastAction` 再回 CDP error**（`kitesurf.control.held`）；读类（`Page.captureScreenshot`、`DOM.*`、`Runtime.evaluate` 只读用途按方法白名单区分）不拦；pane 对被拦的一次给可见回执 | 让「人的接管」在**所有写路**上成立；行为可预期；错误可追溯 |
| B | 只记录不拦截（`lastAction` 记 `relay-blocked` 但照常转发） | 可观测但不可拒，Q3 只解一半 |
| C | 不覆盖 relay，仅在 skill 里写「relay 写不受 humanHold 约束」 | 诚实但把风险留给使用者 |

**推荐 A**。理由：`taken over` 是对人的**承诺**，不是提示。既然 pane 提供了「停止写入」，它必须在 agent 实际使用的通道上生效——否则人无法在与 agent 协作时保护自己的改动。

**需你确认的两点**：① 这是**写入承诺的变更**（relay 从"无限制"变为"可被拦"），属扩约；② 拦哪些方法——我建议只拦"会改页面状态"的三类，`Input.*` 里 `dispatchMouseEvent` 用于点选也算写。

### Q4 — 渲染面默认与 `/dom` 版本字段

**已确认的事实**：默认 HTML（`976b393`）使本地 http 站必然无样式（混合内容），用户看到的"design mode 选不中元素"是其后果；本轮已把默认改为引擎渲染，并给 HTML 模式加同源代理（`dom-srcdoc:106`）。但 `/dom` 的版本字段（`at` vs `capturedAt/domSeq`）是客户端自行合成（`client:4533` 附近 `at: Date.now()`），存在"内容未变也重写 iframe"的隐患。

| 选项 | 内容 | 评价 |
|---|---|---|
| **A（推荐）** | 冻结「默认引擎渲染 + HTML 模式经 `/res`」；同时**把 `/dom` 的版本语义收归宿主**：`/dom` 返回稳定的内容版本（`domSeq` + 内容 `capturedAt`），浏览器端改为只读该字段，不再合成 `at` | 一次把渲染与版本两件事定死；消除重写抖动 |
| B | 只冻结渲染策略，`/dom` 字段不动 | 渲染闭合，但 iframe 重写抖动仍在 |
| C | 回退到「HTML 为默认」 | 与 [业主] 既有裁决相反，不讨论 |

**推荐 A**。

**需你确认的一点**：`/dom` 的字段语义变更（`at` 不再由客户端合成）属**公共响应字段变更**，请批准。

### Q5 — `/res` 的放行范围与边界

| 选项 | 内容 | 评价 |
|---|---|---|
| **A（推荐）** | 放行任意 `http`/`https`；硬边界：仅 http/https、主机不带凭据、单响应 ≤ 24 MiB、15 s 超时、剥离 `Set-Cookie`/CSP/`X-Frame-Options`/`Content-Encoding`、重定向映射回代理空间、越界具名 errorId | design mode 需要外链字体/CSS（实测该站引 `fonts.googleapis.com`），收窄会直接破样式 |
| B | 仅允许私网 / `networking.hostGateway` | 外链样式与字体全挂；且"私网判定"本身依赖运行时拓扑，易漂移 |
| C | 任意外网 + 二次开关（`?allow=public`） | 多一个状态位与一条心智负担，收益不明 |

**推荐 A**。理由：这是一个**受宿主准入保护的只读取资源面**，不是开放代理；它的风险由"仅 http/https + 剥 Cookie + 不带凭据"控制，而不是由目标域名控制。

### Q6 — 公网隧道怎么"禁"？

背景：[业主] 已定性「cloudflared 是完全错误的行为，绕过全部拓扑」。但你此前也要求「对禁止的工作需要明确用 error 禁止」。

| 选项 | 内容 | 评价 |
|---|---|---|
| **A（推荐）** | **警示而非阻断**：`/open` 与 `/res` 命中已知隧道域时，响应附 `hint` 与具名 id（`kitesurf.navigate.public-tunnel` / `res.public-tunnel`），`/diagnostics` hints 同源提示「本地站走 `networking.hostGateway` + `/res`」；skill 里的禁令表已落地（`recipes.md` 配方 5） | 域名黑名单脆弱（隧道域可自建、可换），硬拒绝会误伤合法站点；警示能把人和 agent 都拉回正确路径 |
| B | **硬拒绝**：命中即 `502 navigate.public-tunnel` / `400 res.public-tunnel` | 语义最强，但会被"合法但用了 CDN 域"的场景误伤，且黑名单需要持续维护 |
| C | 只在 skill 里写禁令，代码不检测（现状） | 已经证明不够——那条 session 的 agent 就是自己起了 tunnel |

**推荐 A**。理由：「禁止」的可执行落点是 **skill 的正负例 + 界面/诊断的可见警示**；域名黑名单不是可靠的控制面。若你坚持硬拒绝，我按 B 实现，但请同时批准"黑名单清单"作为**需要维护的配置面**。
